# Мониторинг распределения вероятностей: PSI

Скрипт `src/monitoring/monitor.py` выполняет пункт задания об имитации новых данных:
выбирает часть отложенного теста, отправляет клиентов в работающий `/predict`
и сравнивает распределение оценок API с распределением на обучающей выборке.

## Что делает скрипт

1. Проверяет готовность API через `/health`.
2. Загружает сохранённую модель и её конфигурацию. Обучение не запускается.
3. Получает эталонные вероятности для всех строк `train.csv`.
4. Выбирает до 200 строк из `test.csv` с `random_state=42`.
5. Отправляет каждую выбранную строку в API. В запрос передаются только входные
   признаки модели, без ID и целевого столбца.
6. Сверяет оценки API с сохранённой моделью и проверяет порог и прогнозируемый класс.
   При несовпадении или ошибке запроса расчёт останавливается.
7. Рассчитывает PSI и сохраняет JSON-отчёт и CSV с ответами API.

## Расчёт

Интервалы определяются квантилями **обучающих** вероятностей. Затем одни и те же
границы применяются к эталону и новой выборке. Внешние границы — 0 и 1.
При вырожденном эталоне используются равные интервалы на [0, 1].

По каждому интервалу считаются доли эталона `p` и текущей выборки `q`:

```text
PSI = sum((q - p) * log(q / p))
```

К частотам каждого интервала прибавляется 0.5 с последующей нормировкой.
Это сглаживание обеспечивает конечный результат при пустых интервалах.
В отчёте сохраняются границы, исходные частоты, сглаженные доли и вклад интервалов.

Для учебной интерпретации используются условные уровни:

| PSI | Уровень сдвига |
| --- | --- |
| Менее 0.1 | Низкий |
| От 0.1 до 0.25, не включая 0.25 | Умеренный |
| От 0.25 | Выраженный |

Эти границы являются ориентирами. Значение зависит от размера выборки, числа
интервалов и сглаживания. PSI описывает изменение распределения оценок модели.
Оценка качества классификации требует фактических целевых меток.
Использование части теста здесь является учебной имитацией поступления данных.
Параметры модели и порог после мониторинга не меняются.

## Запуск на Windows через Docker

Используются библиотеки уже собранного образа `credit-default-api:local`.
Папка проекта подключается в дополнительный временный контейнер, который
обращается к API через общую сеть с контейнером `credit-default-api`.

В PowerShell перейти в полную папку проекта, где есть данные и модель.
Проверить API:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health | ConvertTo-Json
```

При остановленном API запустить его и дождаться готовности:

```powershell
docker run --rm -d --name credit-default-api -p 127.0.0.1:8000:8000 credit-default-api:local
```

Запустить мониторинг:

```powershell
$projectDir = (Get-Location).Path
docker run --rm --network container:credit-default-api --mount "type=bind,source=$projectDir,target=/workspace" --workdir /workspace credit-default-api:local python -m src.monitoring.monitor
```

Команда использует `data/processed/train.csv`, `data/processed/test.csv` и
`models/reproduced`. На компьютере появятся:

- `reports/drift_report.json` — PSI, интервалы, параметры выборки, контрольные
  суммы входов и результат сверки API с моделью;
- `reports/drift_report_predictions.csv` — ID, вероятности, классы и порог для
  отправленных в API клиентов.

Посмотреть краткий итог:

```powershell
$report = Get-Content .\reports\drift_report.json -Raw -Encoding UTF8 | ConvertFrom-Json
$report.psi | Select-Object value, level, reference_rows, current_rows, actual_bins
```

Скриншот с выводом скрипта и файлом отчёта подходит для демонстрации мониторинга.

## Запуск в подготовленной Python-среде

Из корня проекта при работающем API:

```bash
python -m src.monitoring.monitor --sample-size 200 --seed 42
```

Параметры: `--train`, `--current`, `--model-dir`, `--api-url`, `--sample-size`,
`--seed`, `--bins`, `--timeout`, `--report`. Дополнительные зависимости не нужны:
используются библиотеки из `requirements-serve.txt` и стандартной библиотеки Python.

## Проверки

```bash
python -m pytest tests/test_monitoring.py -v --tb=short
```

Проверяются нулевой PSI одинаковых распределений, ручной числовой пример,
пустые интервалы, фиксированные границы эталона, вырожденное распределение,
некорректные вероятности и несовпадение модели/порога API.
Интеграционный тест отправляет запросы на локальный HTTP-сервер с тестовой
моделью и проверяет воспроизводимую выборку и сохранённые отчёты.
GitHub Actions запускает эти проверки вместе с остальными тестами.
